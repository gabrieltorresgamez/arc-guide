## Explanation

A building block view shows the parts of a system and how they relate. arc42 says this view should make the source code understandable through abstraction.

arc42 describes the view as levels of black boxes (outside only) and white boxes (inside shown). Level 3 zooms only into selected level 2 blocks.

C4 (see the article C4 Model) points the same way. A component sits one abstraction level above code. It groups related functionality behind an interface. In object-oriented languages, one or more classes implement a component.

**Better alternatives**

- Form building blocks by cohesion. Group code that belongs together by responsibility.
- Create component diagrams only when they add value. Consider automating their creation for long-lived documentation.
- Skip code-level diagrams in long-lived documentation. IDEs can generate them on demand. Keep this detail for the most important or complex components.

## Example

A team documents an order system. Its level 3 diagram shows boxes named OrderFacade, OrderService, OrderDto and OrderConverter, repeated for customers and payments. Every box matches a code package.

A better view shows three blocks: Ordering, Customer Management and Payment. Each groups code by responsibility. A developer who needs package detail generates it from the code with an IDE.

## Trade-offs

Code-level detail has a use. It is warranted only for the most important or complex components.
