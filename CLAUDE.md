# CLAUDE.md

The vision and principles are in README.md ("Vision and principles"). The rules below make them checkable.

Content rules for `content/` (articles are generated by LLM agents from public web sources, then claim-checked):

1. Every statement must be supported by a source listed in the article. Never invent citations or add knowledge from memory.
2. Own words. Do not copy sentences from a source. At most one direct quote per article, at most 25 words, in quotation marks.
3. English (US spelling), plain language for non-architects, no marketing tone. No information about people.
4. Categories, arc42 sections and guide steps come from `taxonomy.yaml`. Never invent new ones.
5. A source must be publicly readable, because the claim check reads the page to verify statements. A paywalled source may only be listed as further reading, never as support for a statement.
6. Diagrams render only through the local Kroki (`KROKI_URL`, default `http://localhost:8000`), never a public renderer.
7. Tactics: name a tactic only if a public source calls it a tactic or approach for that quality. Prefer the SEI/Bass catalogs and the arc42 quality model (quality.arc42.org). Link the matching arc42 approach page where one exists. Vendor patterns (for example Microsoft or AWS guidance) may appear as examples, labeled as that vendor's guidance. Do not invent or merge tactics without a source that does the same.
8. Quality models: use ISO/IEC 25010:2023 only (nine characteristics). Subcharacteristics are listed inside their characteristic page with a short definition and links, not as pages of their own.
9. Entry point first. A page answers: what is it, when does it matter, where to read more. Detail beyond that lives in a linked source, not on the page. Say what is not covered, with a link.
10. All or none. Never cover some members of a set (patterns, notation elements, subcharacteristics, tactics) and skip others. Write one overview page that lists the whole set with links, or no page.
11. One entry point per topic. Do not keep two pages that answer the same question. Merge them.
12. Link the canonical source for a topic: the ISO 25010 summary for qualities, docs.arc42.org for the template, quality.arc42.org for approaches and example requirements, the official spec for notations. Never copy text from docs.arc42.org, quality.arc42.org or aim42.org (all CC BY-SA 4.0) into this CC0 repo; paraphrase and link.
13. A new page needs a reason: it answers a question no existing page answers, it is 150 to 650 words, and it has at least 2 sources. Commit a checkpoint before deleting a group of pages.
14. Never commit or push; the user does.

Titles and slugs: the slug is the title in lowercase with hyphens (max 60 characters; shorten the title instead). A group about one named notation or template (arc42, C4, UML, BPMN) sets `title_prefix` in `taxonomy.yaml`, and every page title in it must start with that prefix (the build fails otherwise). Groups of general concepts have no prefix.

Review pages (`/review/`) are generated checklists, not explainers: titled "Review checklist: arc42 section N, ...", slugged `section-NN-...`, and linked both ways with the explainer page of that section (`ARC42_PAGE` in `pipeline/build.py`).

Fixing claim-check findings: rewrite the whole paragraph or bullet so it stays coherent (keep or restate its label, remove a whole block only if nothing supported remains). Never delete just one sentence: that leaves stubs and sentences with no antecedent ("That removes waste."). After every round of fixes run `uv run python -m pipeline.fixaudit` (compares the pages with HEAD, reports damaged edits, exit code 1 if any) and then the claim check again.

Order inside a sidebar group: optional `order: n` in the front matter (lower first, then A to Z; number in steps of 10 so a page can be inserted later without renumbering); the build fails if two pages of one group share a number. Use it only where a reading sequence exists (arc42 sections, C4 levels, ISO characteristics).
Automated checks (`pipeline/build.py`, fail the build): page under 150 words (opt out with `short_ok: true` in the front matter and a reason in the pull request). Warnings only: over 650 words (opt out with `long_ok: true` for catalog and overview pages), references to unknown concepts, 2011-model wording in quality or tactic pages, tactic pages other than one per ISO characteristic. Warnings only: fewer than 2 sources, no page links to it, "See the article X" with no such page, a page that names another page's title but links it nowhere (add "See X." or put it in `related`). Also fails: two blank lines in a row (left where a block was deleted), a page that refers to itself ("see the article <own title>", left by merges), and a `[src:N]` marker without an Nth source.

Source markers: a sentence with a number, a date or an attribution ("Fowler says") ends with `[src:N]`, the position of its source in `sources:` (1-based). The build renders it as a small link to that source and numbers the Sources list. Add a marker only after checking that source N states it; keep the order of `sources:` stable, or update the markers when you reorder.
Before a release or each quarter run `uv run python -m pipeline.linkcheck` (source URLs reachable, no captcha). Claim check without slugs checks the pages and guides changed since HEAD and fails on `unsupported` or `contradicted` findings. Guides have no sources: every statement in a guide must come from a concept page it links (or a web page it links), and the check compares the guide with exactly those pages (`uv run python -m pipeline.claimcheck guides/s04-quality-requirements`).

Build: `docker compose up -d`, then `uv run python -m pipeline.build`. Tests: `uv run pytest`. Claim check (uses your Claude subscription): `uv run python -m pipeline.claimcheck SLUG [SLUG ...]`, report in `build/reports/claimcheck.md`.
